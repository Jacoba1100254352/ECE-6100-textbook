\section{What Computer Architecture Is}\label{sec:auto-003}
Computer architecture asks how a processor and memory system should be organized to finish useful work efficiently.
``Efficiently'' might mean a shorter wait for one result, more completed jobs per second, or less energy per calculation.
Circuits, fabrication, software, and algorithms set the possibilities; the architect chooses how to arrange the machine within them.

Every architectural decision is a tradeoff among competing goals.
A design that minimizes latency for one task may reduce throughput for a server-style workload.
A design that aggressively improves performance may consume more energy or require expensive cooling.
A design that is elegant on paper may be too costly in area or too difficult to verify at scale.
For this reason, architecture is best treated as constrained optimization: choose structures and policies that best match the target application while respecting implementation limits.


\section{Core Methods: Parallelism, Speculation, and Prediction}\label{sec:auto-004}
Most performance techniques in modern processors can be traced to three closely linked ideas: \textit{parallelism}, \textit{speculation}, and \textit{prediction}.
\textit{Parallelism} increases performance by doing multiple useful operations at the same time.
\textit{Speculation} increases performance by doing work early, before the machine is fully certain that this work will be needed.
\textit{Prediction} estimates uncertain future behavior (for example branch direction or branch target) so speculative work is directed toward the most likely path.
Prediction makes speculation more selective: a good estimate directs early work toward a result the program will actually need.

\paragraph{Classifying common optimizations}\label{par:auto-005a}
This distinction is useful because many architectural features combine these ideas differently.
Packed-word SIMD instructions and multicore processors are primarily forms of parallelism.
The course uses \emph{speculation without prediction} broadly for locality-based choices such as retaining cache blocks in case they are needed again.
That is a useful teaching category, but a cache hit does not necessarily execute an uncommitted instruction, and ordinary buffering need not involve a guess.
Branch prediction is speculation with prediction.
Out-of-order superscalar execution combines both parallelism and speculation because the machine overlaps independent work while also allowing some work to proceed before the final architectural outcome is known.

\subsection{Speculation Without Prediction}\label{subsec:auto-001}
Speculation does not require a learned predictor.
A processor can use a fixed optimistic rule rather than a learned estimate.
For example, it may execute a load before the addresses of older stores are known, assuming that the load will not read a location one of those stores changes.
If the assumption fails, the machine must detect the ordering violation and replay the affected work.
No history-based predictor is required, though one could make that decision more selective.

\paragraph{Related idea: a write buffer}\label{par:auto-006}
A write buffer lets the core continue while a store waits to reach the next memory level.
The important gain is overlap, and the buffer alone does not prove that the store is speculative.
In a machine with precise exceptions, translation and permission faults must be resolved before a store becomes irrevocable.
An uncommitted store can wait in a speculative store queue; a committed store can drain from a buffer later without being a guess about whether the instruction should execute.

\subsection{Speculation With Prediction}\label{subsec:auto-002}
When prediction is added, speculation becomes more selective and usually more efficient.
The processor estimates likely future behavior, executes along the estimated path, and commits the work only if the estimate is correct.

\paragraph{Scheduling the next crew}
The first lecture explains the idea through a building project.
If the framing should finish today, schedule the wallboard crew for tomorrow instead of waiting for confirmation before making the call.\footnote{January 13, 2026 lecture, Notability note \emph{1. Syllabus}, \emph{Recording 2}, approximately 14:41--15:25.}
When the estimate is right, the next job starts sooner.
If the framing is delayed, the crew can arrive before there is work for it, and the early decision has a cost.
The prediction is the estimate about completion; the speculation is acting on it.
Merely making the estimate would not shorten the schedule.

\paragraph{Example: branch prediction}\label{par:auto-007}
Branch prediction is the canonical case.
If the predictor guesses that a branch is taken, instruction fetch and decode proceed down the predicted target path immediately.
A correct guess keeps the front end busy and reduces control-hazard stalls.
An incorrect guess forces the machine to squash the speculative instructions and restart on the correct path, which introduces a misprediction penalty.
The basic tradeoff is straightforward: high prediction accuracy yields high performance; low accuracy can erase the benefit of speculation.


\section{Parallelism by Grain Size}\label{sec:auto-005}
Parallelism is best understood by \textit{grain size}, meaning the amount of work grouped into one concurrent unit.
At the smallest scale, bit-level parallelism appears in wide datapaths and arithmetic logic that operate on many bit positions at once.
A 64-bit adder, for example, processes far more state per cycle than an 8-bit design because the hardware width itself exposes more fine-grained parallel work.

At \textit{instruction-level parallelism (ILP)}, the machine overlaps independent instructions within a thread.
Superscalar issue, out-of-order scheduling, and pipelining all exploit ILP\@.
Consider two arithmetic instructions: \texttt{R1=R2+R3} and \texttt{R4=R5+R6}.
Because neither depends on the other, a dual-issue machine can dispatch them together.
In contrast, \texttt{R1=R2+R3} followed by \texttt{R4=R1+R6} introduces a data dependence that limits overlap.
This illustrates the central ILP limitation: dependencies, control hazards, and hardware resource conflicts bound achievable parallel speedup.

At \textit{thread-level parallelism (TLP)}, multiple threads execute concurrently on multithreaded or multicore hardware.
TLP can provide substantial throughput gains, but only if the workload contains enough independent work and synchronization overhead remains controlled.
Inter-program parallelism is the coarsest common level, where independent processes run simultaneously under an operating system scheduler.
This is the dominant form in desktop multitasking and cloud services, where many programs share the same physical platform.


\section{A Budget of Transistors}\label{sec:transistor-budget}
The January 15 lecture turns the power wall into a design question: if the next chip can contain more transistors, but running it faster would exceed a practical cooling budget, what should those transistors do?\footnote{January 15, 2026 lecture, Notability note \emph{2. ECE 6100}, \emph{Recording 3}, approximately 06:47--08:05; related slides INTRO-18--19.}
A larger cache might avoid more memory trips.
A wider core might execute more independent instructions.
Additional cores might run more threads.
These choices spend the same kind of physical resource on different sources of useful overlap.

The industry shift toward energy-efficient multicore designs in the mid-2000s makes that question concrete; Intel's 2006 Core introduction explicitly emphasized performance per watt and multicore operation.
It did not mean that instruction-level parallelism or single-core improvement had ended.
It meant that more transistors could no longer be treated as a promise of proportionally faster execution for one unchanged program.
The available work, the memory system, and the power budget still decide what the extra hardware can accomplish.

\section{Flynn's Taxonomy}\label{sec:auto-006}
Flynn's taxonomy classifies parallel machines by counting instruction streams and data streams.
In \textit{single instruction, single data (SISD)}, one instruction stream acts on one data stream, matching the traditional scalar uniprocessor model.
In \textit{single instruction, multiple data (SIMD)}, one instruction stream is applied across many data elements in lockstep, which is highly effective for dense data-parallel computations such as vector math, image processing, and many graphics processing unit (GPU) kernels.
The data values may differ across lanes, but the issued operation is the same across the whole SIMD group.

In \textit{multiple instruction, multiple data (MIMD)}, multiple processing elements execute different instruction streams on different data streams.
This is the dominant model for modern multicore central processing units (CPUs), distributed servers, and cluster systems because it supports general-purpose, irregular workloads.
\textit{multiple instruction, single data (MISD)} exists mostly in specialized contexts, such as certain fault-tolerant designs, and is uncommon in mainstream systems.

\subsection{SIMD vs. MIMD}\label{subsec:auto-003}
SIMD and MIMD solve different problems.
SIMD is efficient when the same operation must be applied repeatedly to large collections of data.
Its lockstep execution naturally provides synchronization across lanes, which reduces control overhead.
If different cores or lanes truly follow different code paths at the same time, the machine is no longer acting like classical SIMD for that region; that behavior belongs to MIMD or to a SIMT-style execution model with divergence handling.
MIMD is more flexible because each processor can follow its own control path, but this flexibility introduces synchronization and communication costs that must be managed explicitly by hardware and software.

Modern GPUs often use a hybrid model sometimes called \textit{single instruction, multiple threads (SIMT)}.
SIMT provides a SIMD-like execution efficiency for the hardware while allowing a MIMD-like programming model where each thread appears to have its own scalar program counter.
The hardware manages the divergence and convergence of these threads, grouping those on the same path into SIMD-style execution units.

\paragraph{Representative workload mappings}\label{par:auto-007a}
Simple examples help fix the taxonomy.
A small embedded controller such as a thermostat is usually best viewed as SISD\@.
A dense image transform that applies the same arithmetic to many pixels is a classic SIMD workload.
A cloud-service cluster is naturally MIMD because many processors or machines execute different control paths for different requests.
Some tasks, such as brute-force hash search, can be built in several ways: a lockstep array of identical workers looks SIMD-like, while a farm of largely independent workers looks MIMD\@.
The important step is to identify whether the machine is reusing one instruction stream across many data elements or allowing many instruction streams to proceed independently.

\subsection{Where Pipelining Fits}\label{subsec:auto-004}
Pipelining is orthogonal to Flynn's taxonomy.
It is a temporal form of parallelism in which different stages operate on different instructions concurrently.
Because pipeline structure is an internal execution organization, pipelining can appear inside SISD cores, SIMD engines, and MIMD processors alike.


\section{Vectors: Packed-Word SIMD vs. Pipelined Vector Units}\label{sec:auto-007}
Packed-word SIMD and classic vector pipelines both exploit data parallelism, but they do so with different execution structures.
Packed-word SIMD divides a fixed-width register into lanes (for example, four 32-bit lanes in 128 bits) and applies one instruction across all lanes in lockstep.
An operation such as \texttt{ADD\_PACKED} performs multiple elementwise additions per instruction, and lane boundaries isolate carries so one lane's overflow does not spill into neighboring lanes.
This style underlies CPU SIMD extensions such as streaming SIMD extensions (SSE), advanced vector extensions (AVX), and Arm NEON\@.

Vector pipelines, in contrast, stream long vectors through deep arithmetic pipelines.
A floating-point multiply can be viewed conceptually as operand preparation, multiply, and result normalization/writeback stages.
If a pipeline has $k$ stages and processes $n$ elements, a serial implementation needs $nk$ cycles, while a pipelined implementation needs approximately $k+n-1$ cycles after fill effects are accounted for (Eq.~\eqref{eq:auto-001}):
\begin{equation}\label{eq:auto-001}
    \text{serial cycles} = nk,\qquad
    \text{pipeline cycles} \approx k+n-1.
\end{equation}
The result is substantial throughput gain for long vectors even though single-element latency is not eliminated.

\paragraph{Worked vector-throughput example}\label{par:auto-007b}
Suppose a vector arithmetic pipeline has 6 stages and the program processes 100 elements.
A non-pipelined implementation would spend
\begin{equation}\label{eq:auto-001a}
    nk = 100\times 6 = 600\ \text{cycles}
\end{equation}
to process the vector.
The pipelined form instead needs approximately
\begin{equation}\label{eq:auto-001b}
    k+n-1 = 6+100-1 = 105\ \text{cycles}.
\end{equation}
The difference is the standard vector-pipeline gain: the pipeline still pays 6-stage latency for the first element, but after fill it can accept and complete additional elements at a much higher steady-state rate.

\paragraph{Chaining}\label{par:auto-008}
Vector chaining improves this further.
If a second vector operation consumes results from a first operation, the hardware can forward early produced elements directly into the consumer pipeline instead of waiting for the full vector to complete.
Chaining reduces producer-consumer delay and improves sustained throughput in vectorized loops.

\paragraph{Why the Cray example belongs here}
The introductory slides use the Cray-1 to make vector processing concrete.\footnote{\texttt{n1\_intro.pdf}, INTRO-13--14; see also the Cray manual listed in Appendix~\ref{ch:source-notes}.}
Its vector registers could hold 64 elements, so one vector instruction described a stream of work rather than a single scalar operation.
With chaining, an early element could enter the next functional unit while later elements were still passing through the first.
The useful comparison is to a line of workstations: the second workstation can start on the first item without waiting for the entire batch.
The six-stage calculation above is a teaching model, not a claim about the Cray-1's exact functional-unit latencies.


\section{Common Chapter 1 Pitfalls}\label{sec:auto-008}
A common mistake is to conflate speculation with prediction.
The correct view is that prediction is one way to make speculation more effective, not the definition of speculation itself.
Another recurring error is to assume that additional cores guarantee proportional speedup; real speedup is limited by dependencies, communication, and serial regions of code.
It is also common to treat SIMD and MIMD as interchangeable, even though they target different workload structures and have different programming implications.

A final source of confusion is the difference between packed-word SIMD and long-vector pipelining.
Both process multiple data elements, but packed SIMD exploits lane-level parallel arithmetic within instruction-width registers, while vector pipelines exploit staged streaming over long element sequences.
Related to this, pipelining primarily improves throughput rather than the latency of a single operation.


\section{What to Carry Forward}\label{sec:auto-009}
Look for the work that can overlap, the assumptions that permit it, and the cost of being wrong.
Grain size and Flynn's taxonomy describe different aspects of that overlap.
Packed SIMD uses lanes; pipelined vectors stream elements through stages.
Neither extra lanes nor extra cores can remove a true dependence.
Chapter 2 turns these mechanisms into measurable changes in runtime and throughput.

    \item Classify each of the following workloads using Flynn's taxonomy, and give a one-sentence justification for each answer: a dense image convolution engine, a cloud-service cluster that handles independent requests, a small thermostat controller, and a brute-force hash search implemented as many independent workers.

    \item A vector arithmetic pipeline has 6 stages and processes a vector of 100 elements.
    Compute the approximate cycle count for a serial implementation and for a pipelined implementation.
    Then explain how chaining could reduce producer-consumer delay for two dependent vector operations.
    \item Distinguish packed-word SIMD from classic pipelined vector execution.
    In particular, explain what is fixed by register width in packed SIMD and what is streamed through the pipeline in classic vector execution.
\end{enumerate}
